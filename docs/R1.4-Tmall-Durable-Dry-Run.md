## 用户需求
- 不再使用排班表，不查找新增直播间；按既定顺序只做淘宝／天猫第一家：TCL集团官方旗舰店（历史账号 ID `2050532947`、roomNum `130742`）。
- 只关心直播是否正在进行、首次检测开播、首次检测下播、可验证的直播时长估算。
- 开播期间每 **15 分钟**观察一次；确认下播后本场结束，仅按 **60 分钟**低频检查是否重新开播；如果停止所有请求，就无法自动发现下一场。
- 无需用户本地设备在线，不要求淘宝开发者 API 申请成功；优先零新增费用。

## 本次已实现
1. `probes/lib/r14-tmall-durable.mjs`：**单账号固定身份、JSON可携带状态、定时到期判断、历史状态还原**。结合 R1.3 两次有效 OFFLINE 下播确认、LIVE 时间跨度估算与 UNKNOWN 严格降级。
2. `probes/r14-ledger-dry-run.mjs`：离线模拟无数据源的任务执行，只保存 UNKNOWN，不会发起任何淘宝/天猫页面或 API 请求。每次调用可传上一份 JSON 恢复，新增一次不可伪装为 LIVE 的未连接观测。
3. `tests/r14-tmall-durable.test.mjs`：32 条离线回归，覆盖15/60分钟跳过、跨进程恢复、下一场开始、下播确认、限流、异常、时间和账号冲突、敏感字段截断。
4. `.github/workflows/r14-tmall-durable-offline.yml`：两段隔离 GitHub Actions **作业**，第一段运行测试并创建 `r14-stage1/state.json`，第二段在另一个全新 runner 恢复该制品，再添加一次 UNKNOWN，生成 HTML/JSON/Markdown 报告。**这只验证同一次 workflow 的跨作业移交，不等于已经实现跨天/跨 workflow run 的持久化**。

## 技术关键问题
- GitHub Actions 的 `schedule` **只会在默认分支生效**，无法靠在当前草稿 PR 内添加 schedule 验证无人值守。官方文档：https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows
- Actions artifacts 有保留期，不能把 14 天报告包当作永久数据库；正式版本要另行规划持久化分支或数据库，启用写权限前须确认隔离与隐私。官方：https://docs.github.com/en/actions/how-tos/manage-workflow-runs/download-workflow-artifacts
- **本轮不启用自动真实访问**。此前 Work 浏览器被平台安全策略阻断且淘宝公开探针有 RGV587 风控限流记录；不采用未验证的替代入口绕过。要等到有获准数据源后，再将它接到 `approvedSample`。
- `approvedSample` 是给未来**已经单独验收合规数据源的采集适配器**预留的编程接口，本模块自身只检查结构和目标 ID，不能证明数据是真的。正式运行前还须做来源验证与权限隔离。
- 默认采样丢失后当前状态 `UNKNOWN`；不能从后验报告或历史 LIVE 推断本轮正在开播；不会推定实际开播/下播时刻，不会计正式满播率。
- 当前 CLI 只接受无数据源的 dry-run 操作；没有 LIVE/OFFLINE 手工伪造命令。
- 下播后每60分钟才发现新场次，短直播可能完全漏掉。需要明确承认覆盖率限制。
- R1.3 `estimatedContinuousLiveMinutes` 是相邻 LIVE 的时间跨度估计，不能作为准确分钟数或认定无中断的证明。
