# R3.25 抖音"今天播没播"判定（Claude，2026-11-14）

结论：**可以实现（PASS_WITH_LIMITS）**。判定逻辑、台账、页面和测试已经完成，并用 11-13 两次已批准的真实运行回执做了离线验证。目前只差真实的连续采样，以及对回放这条路的确认，这两项都需要新的授权。

## 1. 需求（用户 2026-11-14 00:20）

- 京东：按固定时段计算满播率（另行处理）。
- 抖音："看看他们这边回放，有没有在今天直播就 OK 了"。也就是按天判断每个账号当天有没有开播，具体做法由 Claude 决定（"交给你"）。

## 2. 判定规则（北京时间，每个账号每天一条）

| 状态 | 条件 | 说明 |
|---|---|---|
| 已开播 `BROADCAST_SEEN` | 当天至少一次采样看到该账号在播 | 依据分两级：**主页与直播间双重核验**（台账 LIVE），或**已核验主页上，本账号直播间显示"直播中"**（只看主页）。只要有双重核验，就报告这一级 |
| 采样中未见开播 `NOT_SEEN_IN_SAMPLES` | 有核验通过的采样，但都没看到在播 | **不等于没有开播**：两次采样之间的短场次可能漏掉 |
| 无法判断 `UNKNOWN` | 当天没有核验通过的采样（被拦截、未执行或身份未核验） | — |

"本账号直播间"的认定：主页身份必须先核验通过（最终 URL 完全一致，且页面上只有一个抖音号并且一致）。在此基础上，"直播中"链接要么位于主播信息区，要么就是页面上唯一的直播间，并且等于该账号登记的直播间。别人的直播间，或者同时出现多个直播间，一律不算。

只看主页得到的依据**不会**把台账状态改成 LIVE。LIVE 仍然需要主页和直播间双重核验。

## 3. 真实数据离线验证（11-13 两次已批准运行的公开回执，没有新的访问）

| 账号 | 采样（北京时间） | 结果 |
|---|---|---|
| #1 | 23:11、23:39 | **已开播**：23:39 那次采样中，已核验主页上本账号直播间显示"直播中"。23:11 那次按旧逻辑没有记录直播间范围，所以不计入 |
| #2 | 23:11、23:40 | **采样中未见开播**：只有夜间两次采样，不代表当天没播 |

## 4. 实现

- `probes/r322/observation-ledger.mjs`：台账新增可选标记 `ownRoomLiveBadge`。它只能由探针自己的字段推导出来，回执不能直接声明；只在为 true 时写入，所以 R3.22 的旧台账不用改也照样有效。新增 `buildDailyBroadcast()` 和 `beijingDay()`。
- `probes/r322/render-ledger.mjs`：离线页面新增"每日开播（北京时间）"一节，页面里没有脚本，也没有链接。
- `probes/r325/daily-report.mjs`：命令行工具，输出每日结果，只包含账号 key、日期、状态、依据、次数和采样时刻。
- 回放诊断（只写入加密的私有记录）：统计原始 HTML 中"直播回放"字样出现的次数，以及含 replay 的 JSON 键名；统计渲染后页面中"直播回放"文本出现的次数，以及它所在位置的标签链。

## 5. 测试

- `tests/r325`：7 个单元测试和 1 个 Chromium 测试。覆盖：标记的推导与防篡改、旧台账兼容、三种状态、北京时间跨日边界、页面措辞、命令行工具、回放诊断。
- 封闭网络端到端（5 个场景）新增两项检查：每日判定（别人的直播间不计入；另一个账号只会显示"采样中未见开播"），以及回放诊断（只检查标签）。
- 全量回归：445 个测试，438 通过，0 失败，7 个跳过（都是浏览器测试，已单独运行，6/6 通过）。

## 6. 限制和下一步

1. 连续采样：正式运行需要在白天定时采样（例如每 2 小时一次），必须在 main 上开启定时任务，需要用户批准。
2. 回放：账号有没有开回放、游客在网页上能不能看到，都还没有验证。需要一次只访问主页的诊断运行（账号不在播时也能跑），需要用户批准。
3. 京东固定时段的满播率：需要用户给出固定时段。
