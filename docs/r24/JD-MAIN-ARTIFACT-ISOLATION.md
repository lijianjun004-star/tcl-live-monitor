# R2.4 京东定时巡检｜主分支状态隔离与验收门禁

日期：2026-11-10，北京时间。此修复针对 R2.3 已启用但尚未观察到真实 `schedule` 触发的默认分支启动器，不更改 Pages 或实际巡检数据。

## 已证实的缺陷
R2.3 的默认分支工作流按仓库全域 `name=r23-jd-state` 获取“最新” Artifact，未要求来源分支为 `main`。2026-11-10 的两轮实验运行确实在 `experiment/r23-jd-unattended-monitor` 分支上传了同名 Artifact，因此默认分支首次定时恢复**可能误读实验历史为正式历史**。此风险不是已发生生产数据污染的证据。

## R2.4 最小修复
1. 仅修改 `.github/workflows/jd-r23-scheduled.yml`，把上传与恢复统一改为专用名称 `r24-jd-main-state`。
2. 读取时严格限定 `workflow_run.head_branch == "main"`、未过期、有同仓库 provenance；缺少符合条件的文件只能按空基线安全初始化，不引入实验历史。
3. `verify-restore-isolation` 仅在 PR / 推送时执行 `tests/r24-main-artifact-restore.test.mjs` 的离线反例测试；`inspect` 仅在 `schedule` / 手动事件执行。
4. 保留 R2.3 的 SHA 固定源代码 `267b6709a8563ef779cda6b11c97b9684c4e1c16`，已有多轮测试的状态机和只读来源逻辑不变。
5. 工作流仍仅具备 `contents: read`、`actions: read` 权限，不使用写仓库权限，不部署 Pages。

**注意：** 新命名空间是刻意清空历史恢复入口，而非迁移旧测试数据。首次合并后出现一次安全初始化属预期。只有 GitHub 实际 `schedule` 事件运行成功后，才可确认主分支的无人干预定时采集；GitHub 的定时任务为尽力执行，并不保证严格分钟级 SLA。

## 真人与数字人分段规则（业务约束，尚未接入视觉分类器）
用户补充的 TCL 业务规律：**数字人只在真人下播后开启，不在真人正在上播期间切换使用**。后续单独记录“店铺在播状态”“真人场次结束”“数字人场次开始”，严禁将店铺持续 LIVE 直接视为真人持续上播；没有画面/回放证据则记 `PRESENTER_UNKNOWN`，不能用同一张脸固定出现来直接证明数字人。京东是否存在具体数字人场次仍需独立实测，不从该业务规则推断当前状态。

## 发布与回滚
此分支只提交草稿 PR 供复验；未合并前旧定时启动器保持原样。合并前须核对源代码不受影响、离线测试通过、主分支 SHA/变更路径仍符合预期，并在合并后检查首次真实 scheduled run、Artifact 来源分支及恢复日志。失败时不伪报 PASS、不自动合并。
